## 回應結尾的 [CTX] 摘要（必須）

每則回應的**最後面**都要附一個 `[CTX]` 區塊。它不會顯示給使用者，而是被存下來，
在下列情況重新餵回給你，避免失憶：

- 開新 session（第一輪、閒置 4 小時過期、bot 重啟、session 失效重試）
- 使用者只回很短的話或「好／可以／繼續」這類同意詞

沒有這個區塊，連續性就只能靠上一則回覆的尾巴硬猜。

### 格式

必須是回應的最後一段，前面空一行：

```
[CTX]
status: done
summary: 修好 splitText 的 fence 保留量，加了回歸測試
pending: none
next: 等使用者決定要不要重啟 bot
files: src/utils/text-splitter.ts, tests/utils/text-splitter.test.ts
[/CTX]
```

### 欄位

- `status:`（**必填**，只能是這六個）
  - `done` — 做完了
  - `proposal` — 提出做法等使用者點頭
  - `question` — 在問使用者問題
  - `options` — 給了幾個選項讓使用者挑
  - `error` — 卡住或失敗
  - `info` — 單純回答／解釋
- `summary:` 這一輪實際做了什麼，一句話，具體（檔名、數字、結論），不要寫「處理了一些事」
- `pending:` 還沒做完、下一輪要接手的事；沒有就寫 `none`
- `next:` 預期的下一步；沒有就寫 `none`
- `files:` 這輪真的讀過或改過的檔案，逗號分隔；沒有就省略這行

### 這些欄位會被累積成「任務檔」

每一輪的 `summary:` 會**追加**進一個任務的決策紀錄（不是覆蓋），`pending:` /
`next:` / `files:` 則代表當前狀態、會被更新。

- 下一輪只會拿到「最近 3 條決策 + 未解決 + 下一步 + 任務檔路徑」，不會拿到全部歷史。
  需要更早的決策就自己 Read 那個路徑。
- 所以 `summary:` 要寫成**一條有保存價值的決策**（做了什麼、為什麼），
  不要寫「繼續處理」這種過幾輪就沒意義的句子。
- `status: done` 代表這個任務結束，下一輪會開一個新任務。
  **沒真的做完就不要寫 done** —— 中途回報進度用 `info`，等使用者決定用 `proposal` /
  `question` / `options`。

### 規則

- `status:` 必須是上面六個字之一，拼錯整個區塊會被丟掉。
- 每個欄位只能一行，不要換行、不要項目符號、不要用 `**`。
- 內容寫給「失憶的下一輪自己」看：省略的細節就是下次要重新查的東西。
- 不要在回應中間放，也不要放兩個。
